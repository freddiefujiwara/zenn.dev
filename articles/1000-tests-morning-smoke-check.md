先に結論を書きます。このサイトで起きた本番障害は、思い出せる限りすべて、プログラムのロジックではなく「設定とつなぎ方」の問題で起きました。デプロイ設定の上書き、呼び出し側の条件分岐の欠落、CIのステップの順序、未設定のシークレット。だからこの記事は、テストの説明よりも先に、実際に起きた障害から書きます。本番障害の学びを、テストや運用の形で残していく。それがこのサイトのやり方です。

この6件の対策を積み上げた結果が、次に説明する3層のテストと運用です。

## 先に、テストの全体像

このサイトのテストは3層です。第1層はUnitテストで、部品1つ1つの動きを確かめます。第2層は設定のテストで、プログラム本体ではなく、設定ファイルの中身が「壊れてほしくない形」のままかを確かめます。第3層はe2eテストで、実際のブラウザでページを開き、部品同士のつなぎ方が正しいかを確かめます。

なぜ3層も必要なのかは、このあとの障害の話を読むと分かります。このサイトで起きた障害は、部品の動きの間違いではなく、設定とつなぎ方の問題ばかりだったからです。

## 実際に起きた障害と対策

### 障害1：GASの再デプロイで、匿名アクセスが止まった

事象：2026年11月1日、裏側のGoogle Apps Script（以下GAS）をCIで再デプロイした直後から、一部のアプリでデータが表示されなくなりました。APIのURL（/exec）にアクセスすると、JSONではなくGoogleのサインイン画面のHTMLが返ってきます。後の監査で見つかった別の仕組みでは影響が長く残り、自宅の状態表示や温湿度の記録が止まって、記録は翌日で止まっていました。

原因：GASのWebアプリの公開範囲は、GASの画面で手動設定した「全員（匿名アクセス）」が正でした。ところがソース側の appsscript.json には webapp.access として "ANYONE" と書かれており、再デプロイのたびにマニフェストの値で手動設定が上書きされ、匿名アクセスが落ちていました。READMEだけの変更でも再デプロイは走るので、この地雷は日常の変更でも踏める状態でした。

対策：(1) appsscript.json の値を "ANYONE_ANONYMOUS" に統一した。(2) その値をテストで固定し、変わったらCIで落ちるようにした（第2層で後述）。(3) 運用として、GAS側のリポジトリを触る前に /exec の応答を記録し、CI完了後に必ず疎通を再確認するようにした。この設定テストを追加したプルリクエストが、[alarm-gas #14](https://github.com/freddiefujiwara/alarm-gas/pull/14) と [everything-i-own-gas #15](https://github.com/freddiefujiwara/everything-i-own-gas/pull/15) です。

### 障害2：ステージングのバナーが、本番の3アプリに出た

事象：ステージング確認用の薄いバナー（「STAGING ― これはステージング環境です（本番ではありません）」）が、本番の3つのアプリに表示されました。

原因：バナーを表示する関数 showStagingBanner()（ソースは blog リポジトリ）自体には環境判定がありません。呼び出し側で isStagingBuild() という判定で囲むのが正しい形で、この3アプリは無条件に呼んでいました。残りのアプリは正しく囲んでいました。つまり部品は正しく、入口での使い方だけが間違っていました。

検出と対策：これを見つけたのは、毎朝の見回りテスト（第3層のスモーク）の初回実行です。全40項目のうち失敗はこの3件だけで、しかもUnitテスト1,073本はすべて通っている状態でした。「部品の正しさ」と「入口でのつなぎ方の正しさ」は別の話だということが、実測で分かりました。呼び出し側を修正し、同じスモークで40件すべて成功することを確認しています。修正のプルリクエストは [blog #44](https://github.com/freddiefujiwara/blog/pull/44) と [everything-i-own-admin #48](https://github.com/freddiefujiwara/everything-i-own-admin/pull/48) です。

### 障害3：CI設定のミスが3種類、同じ日に起きた

(a) ジョブの条件にシークレットを書いた。GitHub Actionsでは、ジョブレベルの if 条件で secrets コンテキストを参照できません。書くとワークフロー全体が無効になり、実行名がファイルパス表示の失敗ランになって、失敗通知メールが大量に届きました。3つのリポジトリで発生しました。条件はブランチ判定だけにし、シークレットの有無で分けたい場合はステップの中で判定する形に統一しました。

(b) ワークフローの下書きに "`<redacted>`" という文字列がそのまま入った。画面表示の段階でマスクされていたシークレット参照を写したもので、デプロイ自体は通るのにステップが失敗する形になりました。下書きを渡す前に grep で混入チェックをすることに加え、テストでも検出するようにしました。

(c) ステージング版の同梱が消えた。Viteのビルドは出力先（dist）を毎回空にします。ステージング版を dist に同梱するステップを本番ビルドより前に置いたため、同梱がビルドで消え、ステージングのURLが404になりました。ステップの順序を直しました。

対策は3件共通で、「設定ファイルを読むテスト」です。ワークフロー内に "`<redacted>`" が無いこと、ジョブの if に secrets が無いこと、ステージング用ビルドが本番ビルドの後にあること、画像生成（OGP）の向き先IDが正本と一致すること。ここでいう正本は、基準としてあらかじめ決めた正しい値のことです。OGP画像を作る仕組みは1つだけ用意して全アプリで共有しているので、その向き先IDがどのリポジトリでも同じ値になっているかを見ています。テストはソースコード以外のファイルも読める、という当たり前が効きました。この設定テストを追加したプルリクエストの例が、[blog #42](https://github.com/freddiefujiwara/blog/pull/42) と [everything-i-own-admin #47](https://github.com/freddiefujiwara/everything-i-own-admin/pull/47) です。

### 障害4：デプロイIDの未設定で、/exec が404になった

事象：[持ち物リスト](https://freddiefujiwara.com/everything-i-own/)の裏側で、画面が向いている /exec が404を返し、一覧が空になりました。GAS自体は正常に動いていました。

原因：CIの DEPLOYMENT_ID シークレットが未設定だと、デプロイのたびに新しいデプロイが作られます。画面が向いている旧デプロイがアーカイブされると、そのURLは404になります。「デプロイに成功した」ことと「画面が見ている先が生きている」ことは別物でした。

対策：DEPLOYMENT_ID を現行のアクティブなデプロイに固定しました。あわせて、マージ後は /exec が想定どおりの件数（このとき225件）を返すところまで確認する運用にしています。

### 障害5：外部データの取得失敗で、シートが空になった

事象：持ち物リストのデータ同期で、157件分のシートが空になりました。

原因：旧実装の順序は「シートを消す → 外部からデータを取得する → 書く」でした。あるとき取得先が、JSONではなくプレーンテキストの "OK" を返しました。HTTPとしては成功です。しかし書き込みは行われず、消えたシートだけが残りました。

対策：順序を入れ替え、「全件を取得できてから、消して、書く」にしました。取得に失敗したら、前回のデータをそのまま残します。破壊的な操作は、材料が揃ってから最後に行う、という原則です。

### 障害6：ステージングの確認で、本番の記事に飛ばされた

事象：2026年11月3日、この記事の下書きをステージングで確認しようとすると、本番にしかない記事のURLに飛ばされ、その記事はステージングには存在しないため、画面が空になりました。本番を見ている読者への影響はありません。

原因：本番とステージングは、同じドメイン（freddiefujiwara.com）で配信しています。記事リストはブラウザの中（localStorage）にキャッシュしていて、その保存キーが本番とステージングで同じでした。ブラウザの保存領域はドメイン単位なので、本番で保存した記事リストをステージング側が読んで、そのIDへ遷移していたのです。キャッシュの読み書きをする部品自体は正しく、キーの分け方という「つなぎ方」の問題でした。

対策：キャッシュのキーを環境ごとに分けました。ステージングでは別のキーを使い、本番のキーは変えていないので、これまでの訪問者のキャッシュはそのまま使えます。あわせて、ステージングでは別のキーに保存されることを確かめるテストを、第1層に追加しました。修正のプルリクエストは [blog #45](https://github.com/freddiefujiwara/blog/pull/45) です。

## 3層をもう少し詳しく

障害を受けて整えてきた3層を、順にもう少し詳しく書きます。

### 第1層：Unitテスト

（1,073本。2026年11月3日に計測した内訳は、画面側770本／GAS側303本。その後、第2層の設定テストを全13リポジトリに追加しています）

部品のロジックを守る層です。具体例を挙げます。[持ち物リスト](https://freddiefujiwara.com/everything-i-own/)のGASは、応答JSONが約101KBあり、保存先（CacheService）の1値100KBという上限を超えるため、20,000文字ずつに分割してキャッシュします。この分割まわりでテストしているのは、サロゲートペアの途中で文字列を切らないこと、チャンク数と総文字数を記録したメタ情報が揃ったときだけキャッシュを信用すること、JSONとして読み直せなければキャッシュを捨ててシートから読み直すことです。ステージングかどうかを判定する isStagingBuild() が、専用のフラグを立てたビルドのときだけ真になることも、この層で守っています。障害2の再発を、部品の側でも防ぐためです。

限界も明確です。入口のファイル（main.js）での呼び出し方や、設定ファイルの中の値までは見ません。障害2と障害3がこの層をすり抜けた理由は、まさにそこです。

### 第2層：設定の不変条件を固定するテスト

障害1と障害3を受けて作った層です。対象はコードではなく、appsscript.json と .github/workflows の中身です。検証しているのは、公開範囲が "ANYONE_ANONYMOUS" であること、ワークフローに "`<redacted>`" が含まれないこと、ジョブの if に secrets が含まれないこと、ステージング同梱のステップが本番ビルドの後にあること、OGPの向き先IDが正本どおりであること、です。

狙いは、「壊れてほしくない設定」を運用ルールの文章ではなく、テストとして固定することです。文章のルールは忘れますが、テストはCIで毎回効きます。通常のVitestとして書けるので、CIの構成変更は不要でした。

### 第3層：e2eテスト（Playwright）。門番と見回り

実ブラウザでページを開き、つなぎ方を守る層です。2種類あります。テストのソースは トップ側のリポジトリの [e2e フォルダ](https://github.com/freddiefujiwara/freddiefujiwara.github.io/tree/master/e2e)で公開しています。

門番（ステージング確認）：プルリクエストのたびにステージング環境へデプロイし、(1) ページが200で返ること、(2) バナーがステージングにだけ出ること、(3) ページが本番側のGASのIDを絶対に呼ばないこと、データを読み込むアプリではステージング側のIDを呼んでいること、(4) 裏側に直接アクセスして、ステージングではダミーのデータが数件だけ返ること、認証が必要なアプリでは401が返ること、を確認します。これは全アプリのリポジトリでブランチ保護の必須チェックになっていて、通らないと本番へマージできません。「お願い」ではなく、仕組みで止める形です。

見回り（本番スモーク）：毎朝6時に、本番とステージングの全アプリ、公開しているAPIの期待値、OGP画像（200で返り、1,000バイトを超えること）まで、計40項目を確認します。障害2はこの初回実行が検出しました。この見回りの仕組み自体も、[blog #43](https://github.com/freddiefujiwara/blog/pull/43) のプルリクエストで入れました。

この層の弱点も書いておきます。遅いこと（全件で7〜10分）。公開直後は反映の伝播待ちで結果が揺れること（対策は、デプロイ後に60秒待つこと、CIではリトライ2回、失敗したときのトレース保存）。そして、確認項目に書いたことしか保証しないことです。ページの中のロジックの回帰は第1層の仕事で、ここでは見ていません。

## まとめ：障害の学びを、テストと運用に残す

障害への恒久対策は、性質によって3種類に分かれました。テストに落とせるもの（設定値、呼び出し方、部品のロジック）。運用の確認として残すもの（マージ後に /exec が実データの件数を返すか）。実装の原則として守るもの（破壊的な操作は最後に行う）。

大事なのは、テストの本数そのものではなく、本番で障害が起きるたびに「何を学んで、どう残したか」が増えていくことだと思っています。学びをテストで表せるものはテストに、表せないものは運用の確認に残す。テストの配分を決める材料は、コードの複雑さではなく、実際に起きた障害の分布です。
